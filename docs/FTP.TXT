FTP.EXE - FTP passive file transfer and directory listing
=========================================================

Purpose
-------
  Downloads or uploads files through an FTP server. Directory listing is
  available with the -l and -n flags.

Usage
-----
  FTP.EXE host[:port] file [-o output] [-u user] [-p pass] [-y|-f] [-r] [-d]
  FTP.EXE host[:port] PUT local [-o remote] [-u user] [-p pass]
  FTP.EXE host[:port] [path] -l [-u user] [-p pass]
  FTP.EXE host[:port] [path] -n [-u user] [-p pass]
  FTP.EXE /?

Flags
  -o name   write to this local file (download) / remote name (PUT).
  -u user   -p pass   FTP login credentials.
  -y, -f    overwrite an existing local file without asking.
  -r        resume: append to an existing file (FTP REST).
  -l / -n   directory listing (LIST / NLST).
  -d        dot progress: print one dot per write instead of the
            "<KB>KB / <KB>KB" counter. The counter is drawn through the
            DSS console while receive is paused, so -d is the way to
            measure how much console work costs on a given link.
            Both progress modes keep that receive pause active until FTP is
            ready to drain the next ESP +IPD block.
            The final 8 KiB plus at most one complete ESP +IPD frame is
            retained in memory and written after receive completes. This
            avoids both disk pauses near close and an RTS stop mid-payload.
  When the local file exists, FTP asks [R]esume / [O]verwrite / [C]ancel;
  -y (or -f) forces overwrite and -r forces resume, with no prompt.

  A clean data-link timeout in a sized download preserves the verified bytes,
  closes the stale links, reconnects, and continues with REST. Before recovery
  FTP prints RX timeout diagnostics (total/expected/held bytes, +IPD parser
  phase, payload-left, last header byte, and UART LSR).
  A UART integrity error (overrun, framing, parity or break reported by the
  16550) during a sized download is handled the same way: the block being
  received is discarded before anything reaches the disk, so the file offset
  stays trustworthy, and FTP reconnects and continues with REST from it after
  printing the LSR diagnostic ("UART LSR accumulated=0xNN, last=0xNN"). Up to
  12 such restarts are made per download. Listings and downloads of unknown
  size cannot restart and still fail with exit status 3.
  The diagnostic tells the two overrun cases apart: "receive FIFO overflowed"
  means the ESP kept sending while the Sprinter could not read (check RTS/CTS
  wiring and BAUD), while "overrun flag while the FIFO was empty" means the
  UART reported an overrun that flow control could not have prevented; such
  glitches are rare and the automatic restart is the intended remedy.

Run NETUP first. FTP.EXE uses the active network connection and does not join
Wi-Fi by itself.

The elapsed time is measured in whole RTC seconds. For very small files (for
example 13 KiB completing in one displayed second), the reported KB/s is only
a coarse estimate and may appear above the physical UART throughput. Use
DLSPEED with a large test body for a representative link measurement.

Examples
--------
  FTP.EXE 192.168.1.36 fbird.zip
  FTP.EXE 192.168.1.36 fbird.zip -o folder\newfile.zip
  FTP.EXE 192.168.1.36 fbird.zip -y
  FTP.EXE 192.168.1.36 PUT LOCAL.BIN -o upload.bin
  FTP.EXE 192.168.1.36 -l
  FTP.EXE 192.168.1.36 pub -n
  FTP.EXE 192.168.1.36:2121 -l -u test -p secret
  FTP.EXE ftp.example.org / -l -u anonymous -p anonymous@

Current Limits
--------------
  - FTP works in passive mode;
  - password is passed on the command line;

If FTP cannot start, run NETRESET, NETUP, then retry the command.

Exit Codes
----------
  0  FTP login, PASV and file download, upload or directory listing completed.
  1  Invalid command line.
  2  Sprinter-WiFi card was not found.
  3  ESP/TCP/UART communication error, timeout, or incomplete transfer.
  4  NETUP session/configuration is missing or invalid.
  5  Local file, runtime memory, or DSS storage error.
  6  FTP server rejected a command, login, PASV, REST, or transfer.
  7  Cancelled by the user (Esc/Ctrl+Z).

  A successful run closes with "FTP done."; a run that ends with status 2-6
  prints its reason and closes with "FTP failed.".

Notes
-----
  "UART RX was held; released." means the Sprinter's UART had stopped the
  ESP (hardware RTS) with nothing left to read, so the ESP could not deliver
  its CIPSEND prompt; FTP released the receiver and went on normally. The
  16550 raises RTS again only when a read empties its FIFO, and a FIFO reset
  issued while stale ESP output sat at the trigger level used to leave it
  low; FTP now drains such output by reading it, so this line should be rare.
  "No '>' from ESP, sending anyway." means the ESP did not print its
  AT+CIPSEND prompt in time, even after that release. FTP then sends the
  control command regardless: a module that is merely slow still takes it,
  and if the ESP really is stuck the following reply wait reports the error.
  Seeing this line now and then is harmless; seeing it on every command is
  worth reporting.
  "ESP rejected CIPSEND: control link is closed." means the ESP answered
  ERROR instead of the prompt because it no longer has the control
  connection (the server or the Wi-Fi link dropped it). Nothing was sent;
  FTP stops with exit status 3. A "busy p..." answer to CIPSEND is retried a
  few times automatically before it is reported as error #9.
