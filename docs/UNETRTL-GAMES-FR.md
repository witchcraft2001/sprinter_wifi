# Фичереквест: UNETRTL.DLL — паритет с UNETESP по игровым доработкам

Внутренний документ для мейнтейнера `sprinter-rtl8019a`. Не входит в
дистрибутив пакета (`tools/artifacts.sh` его не перечисляет) — справочный
материал для параллельной работы над RTL-бэкендом.

## Контекст

В рамках оценки игровой пригодности `UNET*.DLL` и последующей реализации
`UNET_CAP_LISTEN` в UNETESP.DLL (см. [UNETAPI.md](UNETAPI.md) и
[src/include/unet.inc](../src/include/unet.inc)) обнаружился ряд разрывов
паритета между бэкендами. Ниже — конкретные запросы с точными ссылками на
код, обоснованием и критериями приёмки. Разделы упорядочены по приоритету:
корректность/безопасность → покадровая стоимость → LISTEN → инфраструктурные
вопросы.

---

## 1. ASYNCSEND (`UNET_CAP_ASYNCSEND`) — паритет с ESP

**Сейчас:** TCP SEND в UNETRTL — блокирующий stop-and-wait: до
`SEND_ATTEMPTS=4` повторов по `SEND_ACK_TIMEOUT_MS=1000` каждый
(`src/lib/tcp_lib.asm:82-83`), сам цикл — `tcp_lib.asm:1075-1130`. Худший
случай — один вызов SEND блокирует DLL на ~4 секунды без возможности отдать
управление вызывающему.

**Запрос:** реализовать `UNET_OPT_SENDSLICE` + `NERR_AGAIN` по образцу
UNETESP (`docs/UNETAPI.md`, раздел SEND; `src/dll/unetesp.asm` —
`SETUP_ASYNC_MODE`/`SEND_BUFFER_RESUME`/`RES_AGAIN` в
`src/lib/esp_tcp.asm`). `NERR_AGAIN` для этого уже зарезервирован в самом
UNETRTL — см. явный комментарий `unetrtl.asm:567-569`:

```
; ABI's transient-refusal code; NERR_AGAIN is off-limits here
; because unet.inc reserves it for UNET_CAP_ASYNCSEND backends.
```

После реализации — добавить `UNET_CAP_ASYNCSEND` (0x0200) в
`UNETRTL_CAPS` (`unetrtl.asm:116`, сейчас `0x001F`).

**Критерий приёмки:** SEND с активным `UNET_OPT_SENDSLICE` возвращает
`NERR_AGAIN` вместо блокировки при молчании канала дольше заданного
кванта; повторный вызов с теми же `channel/buffer/length` продолжает
транзакцию без дублирования байт (тот же контракт, что и в UNETESP).

## 2. UDP `RECV(0)` — лишний тик перед проверкой бюджета

**Сейчас:** `src/lib/udp_lib.asm:373-386` — в цикле ожидания UDP-приёма
1-мс тик (`TICK_AND_CHECK_KEY`) выполняется ДО декремента оставшегося
бюджета:

```
.TICK						; ring empty or budget spent
	CALL	@MAIN.TICK_AND_CHECK_KEY
	JR	C,.CANCEL
	LD	HL,(UDPLIB_TIMEOUT_LEFT)
	DEC	HL
	LD	(UDPLIB_TIMEOUT_LEFT),HL
	...
```

Из-за этого неблокирующий опрос (`timeout=0/1`) всегда платит ~1 мс,
даже когда кольцевой буфер уже пуст и результат заранее известен.

**Образец фикса уже есть в этом же файле**, в TCP-версии того же паттерна —
`src/lib/tcp_lib.asm:1281-1295`, с готовым поясняющим комментарием:

```
.TICK					; reached every pass
	; Consume the budget BEFORE the 1 ms tick: the final pass then
	; returns without a wasted delay. ...
	LD	HL,(TCP_TIMEOUT_LEFT)
	DEC	HL
	LD	(TCP_TIMEOUT_LEFT),HL
	LD	A,H
	OR	L
	JR	Z,.TIMED_OUT
	CALL	@MAIN.TICK_AND_CHECK_KEY
	JP	C,.CANCEL
	JP	.LP
```

**Запрос:** перенести `DEC HL`-проверку бюджета в `udp_lib.asm` перед тиком,
по образцу `tcp_lib.asm`. Однострочный по сути патч, но покадрово значим —
любой игровой цикл, поллящий UDP `RECV(0)`, платит эту миллисекунду каждый
кадр.

**Критерий приёмки:** `RECV` с `timeout≤1` и пустым кольцевым буфером
возвращает `NERR_OK/DE=0` без задержки (или с той же задержкой, что и TCP
`RECV(0)` сейчас — измеримо близко к нулю).

## 3. `ISA_OPEN`/`ISA_CLOSE` — дисциплина IFF (маскирования прерываний)

**Сейчас:** `src/lib/isa.asm:61-79` — `ISA_CLOSE` на пути реального закрытия
делает безусловный `EI`:

```
ISA_CLOSE
	PUSH	AF,BC
	LD	A,(IS_OPEN)
	OR	A
	JR	Z,CLOSE_ALREADY
	...
	XOR	A
	LD	(IS_OPEN),A
	POP	BC,AF
	EI				; system page restored -- safe to take IRQs again
	RET
CLOSE_ALREADY
	POP	BC,AF
	RET				; preserve caller's current interrupt state
```

`ISA_OPEN` (`isa.asm:26-35`) аналогично делает безусловный `DI` ещё до
проверки `IS_OPEN`:

```
ISA_OPEN
	DI				; MMU3 now maps ISA, not the system page the
					; 50Hz ISR runs from ...
	PUSH	AF,BC
	LD	A,(IS_OPEN)
	OR	A
	JR	NZ,OPEN_ALREADY	; keep IRQs disabled while ISA remains mapped
```

Для игры, которая держит прерывания включёнными ради музыкального
плеера/таймера, вызов сетевой функции безусловно гасит и снова зажигает
IRQ, независимо от того, был ли он реально нужен в этот момент, и не
восстанавливает исходное состояние IFF вызывающего при вложенных
open/close парах.

**Запрос:** сохранять/восстанавливать реальное состояние IFF вызывающего
(идиома `LD A,I` / `JP PO,...` для чтения текущего IFF2 без разрушения
флагов, либо явный флаг-параметр) вместо безусловных `DI`/`EI`. Задокументировать
итоговое поведение `ISA_OPEN`/`ISA_CLOSE` в контракте библиотеки — что именно
гарантируется вызывающему при вложенных вызовах.

**Критерий приёмки:** `ISA_OPEN`/`ISA_CLOSE`, вызванные с прерываниями
включёнными и без реальной активности ISA-моста, не выключают/включают
IRQ там, где это не требуется; вложенная пара open/close не оставляет IRQ
в состоянии, отличном от того, что было до внешнего вызова.

## 4. LISTEN (`UNET_CAP_LISTEN`, слоты 18/19) — паритет по контракту и функции

### 4.1 Контракт — уже определён, копировать как есть

`src/include/unet.inc` — файл, который `tools/build.sh:45-59` в этом
репозитории сверяет байт-в-байт с копией в `sprinter_wifi/network`
(переменная `UNET_ABI_SRC`, по умолчанию `../sprinter_wifi/network`):

```sh
abi_ref="${UNET_ABI_SRC:-$repo_root/../sprinter_wifi/network}/src/include/unet.inc"
abi_local="$repo_root/src/include/unet.inc"
if [ -f "$abi_ref" ] && [ -f "$abi_local" ]; then
  if ! cmp -s "$abi_ref" "$abi_local"; then
    echo "Error: $abi_local differs from the frozen UNET ABI at $abi_ref" >&2
    diff -u "$abi_ref" "$abi_local" >&2 || true
    exit 1
  fi
fi
```

**Запрос:** скопировать `src/include/unet.inc` из `sprinter_wifi/network`
(текущая версия контракта) в `sprinter-rtl8019a/src/include/unet.inc`
байт-в-байт, в том же изменении, где начнётся работа над LISTEN — иначе
`make build`/`tools/build.sh` в RTL-репо начнёт падать на гейте сразу после
следующего обновления UNETESP-стороны. Уже определено и зарезервировано:

- `UNET_FN_LISTEN EQU 18` / `UNET_FN_UNLISTEN EQU 19` — семантика: LISTEN
  запускает пассивный приём на порту, поднимает бит `UNET_ST_LISTEN`;
  первый входящий пир переводит канал в `UNET_ST_CONN|UNET_ST_ACCEPT`;
  консьюмер узнаёт об этом, поллируя `RECV` (контракт `STATUS` — только
  память, сети не касается); закрытие принятого соединения возвращает канал
  в LISTEN на том же порту; `UNLISTEN` останавливает сервер насовсем.
- `UNET_CAP_LISTEN EQU 0x0020` — уже был зарезервирован, теперь имеет
  реализацию на стороне ESP (UNETESP `v0.3.0` рапортует `0x033F`).
- `UNET_ST_LISTEN EQU 0x0001`, `UNET_ST_ACCEPT EQU 0x0008` — новые биты
  STATUS.

### 4.2 Реализация в UNETRTL — пассивный TCP-приём отсутствует полностью

`src/lib/tcp_lib.asm` реализует только активное открытие соединения:

- Комментарий `tcp_lib.asm:5`: `* TCP.OPEN -- send SYN, wait SYN+ACK, send ACK, set ...`
- `BUILD_SYN` (`tcp_lib.asm:374-420`) жёстко ставит `TF_SYN` в одиночку
  (`LD A,TF_SYN` на `:420`) — нет варианта `SYN+ACK`.
- `WAIT_SYN_ACK` (`tcp_lib.asm:847-853, 924-927`) принимает ТОЛЬКО пару
  `SYN+ACK` в ответ на наш собственный SYN, под заранее выбранный кортеж
  `(local_port, remote_ip, remote_port)`.
- Состояний нет — `ST_SYN_SENT EQU 1` (`tcp_lib.asm:143`) единственное;
  `ST_LISTEN` отсутствует.
- Входящий "голый" SYN нигде не порождает TCB — путей его обработки нет
  вообще.

**Запрос — минимальный набор для паритета:**

1. Новое состояние `ST_LISTEN` + слушающий порт (backlog=1, под
   `CIPSERVERMAXCONN=1`-эквивалент ESP-стороны — заводить TCB только на
   один одновременный accept, как сделано в UNETESP).
2. Путь создания TCB из входящего SYN на слушающем порту: приём SYN →
   `BUILD_SYNACK` (новый билдер: `TF_SYN|TF_ACK`, аналог `BUILD_SYN` но
   с ACK нашего seq) → ожидание финального ACK от пира → TCB переходит в
   ESTABLISHED.
3. Демультиплексирование входящих сегментов по полному кортежу
   `(local_port, remote_ip, remote_port)`, а не только по `local_port` —
   иначе второй клиент на тот же порт после закрытия первого конфликтует
   с полуоткрытым состоянием.
4. UDP-рандеву — дешевле: `UDP.MATCH` уже существует в UNETRTL; нужно
   лишь фиксировать peer по первому входящему датаграму (симметрично
   ESP-стороне: `AT+CIPSTART=<ch>,"UDP","host",<rport>,<lport>,2` —
   режим 2 = "peer может смениться", реализовано в
   `sprinter_wifi/network/src/dll/unetesp.asm:1494-1558`, `CMD_UDP_MODE`).
   Для UDP LISTEN, скорее всего, изменения в UNETRTL не нужны — только
   контрактная обвязка `UNET_FN_LISTEN`/`UNLISTEN`, которая при
   `UDP`-семантике сводится к "открыть локальный порт и ждать первый
   датаграм", без TCB/SYN-машины вообще.

### 4.3 Бюджет размера — LISTEN не влезает без предварительной работы

**Текущий запас:** `ASSERT $ <= DLL_IMAGE_ORIGIN + 0x38C7`
(`unetrtl.asm:2522-2525`) — **запас 131 байт** (0x38C7 - фактический размер
образа). BSS `DLL_BSS_SIZE EQU 0x0E35` (3637 байт) лежит ВНУТРИ этого же
образа (`unetrtl.asm:192-214`), так что рост кода и рост BSS конкурируют за
одни и те же 131 байт. TCP passive-open состояние (SYN+ACK билдер, ST_LISTEN,
demux по полному кортежу) с высокой вероятностью не влезет в этот остаток.

**Мы рассматривали и НЕ рекомендуем "win320-трюк"** (затирание
релокационного битмапа libman оверлеем поверх мёртвого пространства) —
причина в самом загрузчике libman: оба известных нам загрузчика (свежий
port из `sources/libman` и его прежняя версия) резервируют физическую
страницу под библиотеку только по размеру **образа**, а не образа+битмапа
(смещение читается из заголовка +4). Зона битмапа НЕ резервируется и может
быть отдана ПОД ДРУГУЮ библиотеку, если libman подселяет несколько DLL на
одну 16К-страницу. Проверьте, справедливо ли это же для загрузчика,
используемого в RTL-репозитории, прежде чем рассчитывать на этот трюк —
если справедливо, безопасный доход от него ограничен `align256(image+reloc)
- image` (≈ размер битмапа минус выравнивание), а не полными ~1.8 КБ файла.

**Рекомендованный путь (по образцу UNETESP этой сессии):**

1. Ревизия мёртвого кода в текущей сборке DLL — по аналогии с тем, как в
   UNETESP освободили 1854 байта, обернув одноканальные
   OPEN/CLOSE/RECEIVE-пути в `IFNDEF ESP_TCP_MUX` (эти пути остаются
   доступны для отдельных утилит, которые тот же `tcp_lib.asm`/`udp_lib.asm`
   тоже используют, но не нужны внутри самой DLL). Проверьте, есть ли в
   `tcp_lib.asm`/`udp_lib.asm` аналогичные условно-неиспользуемые внутри DLL
   куски (например, код, нужный только линкуемым утилитам типа
   `tcptest`/`udptest`, но не самой DLL).
2. Если этого недостаточно — общая WIN0-cold-инфраструктура, обсуждавшаяся
   в рамках той же игровой оценки: вторая GETMEM-страница с холодным кодом,
   прямой порт-маппинг WIN0 (порт `PAGE0`, см. `sprinter.inc` в
   `sprinter_wifi/network`) вместо DSS-вызовов, одна фикс-`ORG`-копия (в
   отличие от win320: WIN0 имеет фиксированную базу 0x0000 → не нужны 4
   релоцированные копии), int-thunk на `0x0038` на время холодных вызовов
   (NETINIT/CONNECT — секунды, DI убил бы музыку). Этот механизм
   стратегически общий для обоих бэкендов (закрывает и рост LISTEN, и
   DSS-независимость для игрового режима) — имеет смысл проектировать один
   раз и переиспользовать.

**Критерий приёмки этого пункта:** перед тем как писать TCB-машину для
LISTEN, подтверждён источник ≥300-500 байт свободного места (реалистичная
оценка сложности demux+SYNACK-путей) любым из вышеперечисленных способов.

## 5. Справочно — текущее состояние UNETRTL (проверено на момент письма)

- `UNETRTL_CAPS EQU UNET_CAP_TCP | UNET_CAP_UDP | UNET_CAP_RESOLVE | UNET_CAP_PING | UNET_CAP_MULTICHAN`
  (`unetrtl.asm:116`) = `0x001F`. Комментарий прямо над ним:
  `; LISTEN/TRANSPARENT are v1 gaps.` (`unetrtl.asm:112`).
- Версия — `src/include/version.inc:13`: `DEFINE PACKAGE_VERSION "0.2.56"`.
  Нет отдельного `UNETRTL_VERSION`-файла (в отличие от
  `UNETESP_VERSION` в `sprinter_wifi/network`) — версия зашита в один общий
  `PACKAGE_VERSION`.
- TCP `RECV(0)` уже мгновенный — бюджет проверяется ДО тика
  (`tcp_lib.asm:1281-1286`), это и есть образец для фикса п.2.
- Контракт: `UNET_ABI_VERSION EQU 0x0100` (тот же, что в
  `sprinter_wifi/network/src/include/unet.inc:44`) — паритет по ABI-версии
  сохраняется автоматически при копировании файла (п. 4.1).

## Порядок работы

Рекомендуемая последовательность (независимые пункты можно делать
параллельно, но 1-3 не блокируются друг на друге и на LISTEN):

1. П. 2 (UDP-тик) — тривиален, чинить сразу.
2. П. 3 (IFF-дисциплина) — тоже небольшой, но требует аккуратной проверки
   вложенных вызовов на реальном железе/эмуляторе.
3. П. 1 (ASYNCSEND) — самостоятельная задача среднего размера.
4. П. 4.3 (бюджет) → 4.2 (SYNACK/demux) → контракт уже готов (4.1) —
   синхронизировать `unet.inc` В ТОМ ЖЕ коммите, где включается
   `UNET_CAP_LISTEN` в `UNETRTL_CAPS`, чтобы гейт `tools/build.sh` не ловил
   промежуточное рассогласование.
